# Security policy

Hexis stores secrets, so security reports are the most useful kind of contribution. Thank you for taking the time.

## Status you should know about

Hexis is **pre-1.0 and has not been independently audited.** The cryptography uses well-reviewed primitives
(see [`ai-docs/CRYPTO_SPEC.md`](ai-docs/CRYPTO_SPEC.md)), but the way they are put together, the storage layer, the
Stage 1 gate and the importer have had no third-party review. Do not rely on it as your only copy of anything you
cannot lose, and keep an independent backup.

The honest limits of the design are written down in [`ai-docs/ARCHITECTURE.md`](ai-docs/ARCHITECTURE.md) §3 (threat model)
and §5 (what the Stage 1 gate does and does not protect). A report that restates one of those documented limits is
welcome as a discussion, but it is not a vulnerability.

## Supported versions

Only the latest release and the current `main` branch receive fixes while the project is below 1.0.

## How to report a vulnerability

**Please do not open a public issue for a security problem.**

Use GitHub's private reporting: open the repository's **Security** tab, choose **Report a vulnerability**, and describe:

* what you found and which component it is in (`crypto/`, `storage/`, `commands/`, the importer, the Android shell, the CI workflows);
* the version or commit, and the platform;
* the smallest steps or file that reproduce it;
* what an attacker gains (read a secret, bypass the master password, forge or roll back data, run code).

Never put real passwords, vault files, seeds or exports in a report. Use a throwaway vault.

You can expect an acknowledgement within a week and a status update as the fix progresses. This is a volunteer-run
project: there is no bug bounty and no fixed fix-by date, but a confirmed problem in the cryptography, in how keys are
handled, or one that exposes plaintext is treated as the top priority. You will be credited in the release notes unless
you ask not to be.

## In scope

* Any way to read vault contents, keys, the master password, one-time-code secrets or drive files without the master password.
* A way for the webview, a malicious import file, or a malicious storage provider to make the core reveal or damage secrets.
* Tampering or rollback that the design claims to detect but does not.
* A build or release-pipeline problem that could ship altered binaries (see `.github/workflows/`).
* Plaintext secrets in logs, error messages, temporary files or crash output.

## Out of scope

* An attacker who already controls the unlocked device (root malware, a keylogger, a debugger on the running process).
* A weak master password.
* Findings that need physical access to a device that is **unlocked**.
* Denial of service by a user against their own local vault.
* The documented limits: the gate is a privacy screen and not encryption; a copied data folder resets the attempt
  counter; an overwrite cannot be proven on SSD or copy-on-write file systems.

## Verifying a download

Every release publishes a `SHA256SUMS` file next to the binaries:

```
sha256sum -c SHA256SUMS --ignore-missing
```

Android APKs from a tagged release are signed with the project's release key. APKs from the rolling `nightly`
pre-release are signed with a throw-away key generated by that one CI run: they install, but cannot update an app
installed from a different build.

## The one-line installer and the package repositories

`curl -fsS <site>/install.sh | sh` runs a script from this project's Pages site, so you are trusting that site, GitHub
and TLS. Read the script first (it is [`scripts/install.sh`](scripts/install.sh); the site shows the same text), or run
it with `--dry-run`, which prints the plan and every command and changes nothing.

* Debian, Ubuntu, Fedora, RHEL, openSUSE and Arch installs go through package repositories on the same site. They are signed
  with one project key (apt: `InRelease`, `Signed-By`; rpm: `gpgcheck=1` and `repo_gpgcheck=1`; pacman: `SigLevel = Required DatabaseRequired` with the key locally signed). The installer fetches
  that key from the site the first time (trust on first use). The Download page prints the key's fingerprint once the
  repositories exist, so you can compare it with what your package manager shows when it imports the key.
* Everything else is downloaded from the GitHub release and checked against that release's `SHA256SUMS`. That catches
  corruption and a bad mirror; it does not help if the release itself was replaced, because the list comes from the
  same place.
* The repositories carry stable releases only, never the `nightly` pre-release.
* If the signing key is ever lost or leaked, the project will say so in the security advisories and the release notes,
  and every user must import the new key. Report a suspected key compromise through the private channel above.
